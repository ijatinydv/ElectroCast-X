# 04 — Data contract

The most important document. Scenario JSON is generated by `scripts/generate-scenarios.ts` (seeded, deterministic) and validated by `scripts/validate-scenarios.ts`. **Never hand-edit generated JSON.**

## Time model
- 12 keyframes per scenario at `t = −60, −50, −40, −30, −20, −10, 0, +10, +20, +30, +45, +60` (minutes relative to forecast time `T0`).
- `t ≤ 0` are observations (`kind: "obs"`), `t > 0` are model forecasts (`kind: "forecast"`).
- Scenarios also carry `outcome` for retrospective "Prediction vs Actual".
- The UI holds a continuous `timeMin` in [−60, +60] and interpolates between keyframes.
- Wall-clock display: `T0` is 16:00 IST in every scenario. Scenario-specific date is fixed and shown as "Simulated".

## Headline risk (defined once)
**Risk = probability of first lightning (or, for an electrified cell, of lightning within the corridor) within 30 minutes.** Always labelled `30-min risk`. Countdown probabilities are 15/30/60; the headline is always the 30 value. The sensor lab table therefore changes the 30-min value.

### Scenario C (Sensor failure), cell `C-C11`
- Radar goes offline at `t = −10` (keyframe index 5). Radar `dataAgeMin` becomes null and status `offline` from then on.
- 30-min risk at t = 0 with radar down: 58% (baseline before failure: 74%). Confidence: Low to Moderate.
- Corridor widens smoothly from `t = −10` onward, driven by `widthScale` (below), not hand-set.
- Lightning network status `delayed` (age 11 min) at t = 0, to show the stale-source case.

## Consistency invariants (enforced by `check:data`)
1. `p15 ≤ p30 ≤ p60` and every probability in [0, 1] for all cells, all frames.
2. `firstFlash.windowMin` is `[lo, hi]` with `lo < hi`; if `p15 < 0.5 < p30`, then window midpoint is in (15, 30).
3. Scenario A: `outcome.firstFlashMin` lies within the t = 0 window.
4. `headlineRisk === p30` for first-flash cells; for active cells it equals `activeRisk30`.
5. Corridor nesting: `inner ⊂ outer` and `center` inside `inner`, for 15/30/60. Outer area at 60 ≥ outer area at 30 ≥ 15.
6. Sensor table: for every one of the 16 masks the risk is between climatology floor (12%) and the all-sensors value, and never increases when a sensor is switched off.
7. Every frame's `sensorHealth` matches the scenario story (C: radar offline from index 5).
8. All coordinates fall inside Odisha's bounding box (approx lon 81.3–87.5, lat 17.7–22.6).
9. Every numeric field shown in the UI exists as a field here or is computed by a function in `src/lib/derive`.
10. Evidence rows use only these variables: `cloudTopCooling`, `zdrColumnLevel`, `kdpCore`, `echoTop`, `cape`, `flashRate`, `mixedPhaseGrowth`, `freezingLevel`.

## Schema (TypeScript, in `src/types/scenario.ts`)

```ts
type SensorId = "radar" | "insat" | "lightning" | "nwp";
type SensorStatus = "online" | "delayed" | "offline";

interface Scenario {
  id: "A" | "B" | "C";
  name: string; story: string;
  region: { bbox: [number, number, number, number]; center: [number, number]; zoom: number };
  t0IsoIst: string;                 // e.g. "2026-05-14T16:00:00+05:30" (simulated)
  frames: Frame[];                  // length 12
  sensorTable: Record<CellId, Record<string /* 4-bit mask */, number>>; // 16 masks per cell
  outcome: Outcome;
  events: TimelineEvent[];          // first flash, warning issued, outcome
}

interface Frame {
  t: number;                        // minutes relative to T0
  kind: "obs" | "forecast";
  cells: Cell[];
  lightning: Flash[];               // observed (t ≤ 0) or predicted (t > 0) flashes
  sensorHealth: Record<SensorId, { status: SensorStatus; dataAgeMin: number | null }>;
  flashDensity: number[][];         // low-res grid, e.g. 48×32, flashes/km²/h normalised 0–1
}

interface Cell {
  id: string;                       // "C-A07"
  centroid: [number, number];       // lon, lat
  radiusKm: number;
  reflectivityDbz: number;
  stage: "developing" | "mixed-phase growth" | "electrified" | "mature" | "decaying";
  mode: "first-flash" | "active";
  cloudTopCoolingKmin: number;      // K per 5 min shown as K/5min
  echoTopKm: number;
  zdrColumnLevel: "0C" | "-10C" | "-20C" | "none";
  kdpCore: number;                  // deg/km
  updraftMs: number;
  cape: number;                     // J/kg
  freezingLevelKm: number;
  flashRate: number;                // flashes/min, 0 for first-flash cells
  motion: { dirDeg: number; speedKmh: number };
  corridors: Record<"15" | "30" | "60", { center: [number, number][]; inner: [number, number][]; outer: [number, number][] }>;
  decomposition: { motion: number; growth: number; initiation: number; initiationSites: [number, number][] };
  firstFlash?: { p15: number; p30: number; p60: number; windowMin: [number, number]; confidence: "Low" | "Moderate" | "High"; region: [number, number][]; minutesSinceAppeared: number };
  activeRisk30?: number;
  headlineRisk: number;
  evidence: Evidence[];
}

interface Evidence { variable: string; label: string; direction: "up" | "flat" | "down"; delta: string; sparkline: number[]; }
interface Outcome { firstFlashMin?: number; observedFlashes: Flash[]; observedPath: [number, number][]; }
type CellId = string;
interface Flash { lonLat: [number, number]; tMin: number; altKm?: number }
```
The X-ray voxel volume is **procedural**, generated at runtime from `Cell` fields (`echoTopKm`, `zdrColumnLevel`, `kdpCore`, `updraftMs`, `freezingLevelKm`, plus a fixed seed), not stored in JSON.

## Derived functions (`src/lib/derive`, pure, unit-tested)

```
maskBits(mask): 0–15                       // radar=1, insat=2, lightning=4, nwp=8; bit set = sensor OFF
riskFor(scenario, cellId, mask): number    // looks up scenario.sensorTable[cellId][maskBits]
contributionFor(scenario, cellId): { top: SensorId; sentence: string }
widthScale(mask, sensorHealth): number     // see formula
corridorFor(cell, horizon, scale): polygons
countdownFor(cell, mask): { p15, p30, p60, windowMin, confidence }
exposureFor(corridor, assets): { villages, schools, hospitals, transmission, arrivalMin }
```

### Sensor table generation (in the generator, not at runtime)
Single-sensor drops come from the canonical table above. For k ≥ 2 sensors off:
`risk = max(0.12, base − (Σ dropᵢ) × 0.85^(k−1))`. Precompute all 16 masks per cell.

### Width scale (corridor uncertainty)
`widthScale = 1 + 0.35·radarOff + 0.15·insatOff + 0.10·nwpOff + 0.20·lightningOff + stale`
where `stale = min(0.25, max(0, (worstDataAgeMin − 10) / 60))` over sensors still on. Outer boundary scales by `widthScale`; inner by `1 + (widthScale − 1) × 0.5`.

### Contribution sentence
Generated from the largest single drop plus the cell's evidence, e.g. "Radar contributed most strongly because of rapid mixed-phase growth near −10 °C." The variable phrase comes from the cell's top evidence row for that sensor (radar → mixed-phase growth / ZDR column, insat → cloud-top cooling, lightning → flash rate, nwp → CAPE).

## Geo and assets
- Base geometry: Odisha state and district boundaries, simplified to under 150 KB total (source: `udit-001/india-maps-data`, Odisha GeoJSON; verify licence and district count; simplify with mapshaper).
- **Synthetic** (labelled): villages (name, population, lonLat), schools, hospitals, airports (real ones may be used for airports), transmission lines (polylines), mines, outdoor events. Use plausible but invented names for villages; never imply real casualty exposure.
- Exposure counts in every panel show a `synthetic` chip.
